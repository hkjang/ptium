# Ptium v1.28.0

**느리게 쓰이고 있던 덱을 다른 워커가 가져가고 있었습니다.** 두 워커가 같은 덱을
동시에 쓰고 있었다는 뜻입니다.

## 무엇이 문제였나

워커가 죽으면 그 덱은 다시 큐로 돌아가야 합니다. 그 판단 기준이 **"시작한 지 10분이
지났는가"** 였습니다. 이것은 *아직 누가 쓰고 있는가*가 아니라 *얼마나 걸리는가*에 대한
추측입니다.

이 제품의 설정 설명에도 이렇게 적혀 있습니다 — **"자체 호스팅 122B 모델은 사고를 켜면
5분 이상 걸립니다."** 여기에 **생성 후 자동 수정(repair passes)** 을 최대 10회까지 걸 수
있습니다. 한 번의 생성이 10분을 넘는 것은 고장이 아니라 **정상**입니다.

측정해 봤습니다.

```
첫 번째 워커가 덱을 가져감 (아직 모델을 기다리는 중)
11분 경과
두 번째 워커가 같은 덱을 가져감      ← 같은 덱을 둘이 씁니다
```

모델 비용이 두 배로 들고, 나중에 끝난 쪽이 먼저 끝난 쪽의 결과를 덮어씁니다.

## 살아 있다고 말하게 했습니다

워커는 덱을 쓰는 동안 **30초마다 살아 있다고 말합니다**(heartbeat). 이제 덱을 회수하는
기준은 **"3분 동안 아무 말이 없었는가"** 입니다.

- **느리지만 살아 있는 생성은 아무도 건드리지 않습니다** — 30분이 걸려도 그대로입니다.
- **정말 죽은 워커의 덱은 10분이 아니라 3분 만에** 큐로 돌아갑니다.

또한 각 시도는 **자기 임대(lease)** 를 갖습니다. 덱을 잃은 워커는 —

- **완료도 실패도 기록할 수 없습니다.** 지금 그 덱을 쓰고 있는 시도를 덮지 않습니다.
- **스스로 멈춥니다.** 다음 heartbeat에서 "이 덱은 더 이상 우리 것이 아니다"를 알고
  진행 중인 작업을 취소합니다.

## 검사

데이터베이스를 붙여 실제로 확인합니다.

1. 30분째 쓰고 있으면서 살아 있다고 말하는 덱 → **아무도 가져가지 못합니다.**
2. 말이 끊긴 덱 → **다른 워커가 가져갑니다**(다른 임대로).
3. 덱을 잃은 워커의 실패 보고 → **무시됩니다.** 덱은 지금 주인의 것으로 남습니다.
4. 지금 주인의 완료 보고 → **기록됩니다.**

10분 규칙으로 되돌리면 1번에서 실패합니다.
