# Ptium v1.54.0

**슬라이드를 "발표에서 건너뛰기"로 표시하면 발표가 엉뚱한 장을 띄웠습니다.**

## 버튼이 약속한 것

편집기의 그 버튼은 이렇게 말합니다.

> 발표할 때 이 슬라이드를 건너뜁니다. 덱과 내려받은 파일에는 그대로 남습니다.

앞 문장은 지켜지지 않았습니다.

## 실제로 그린 것을 쟀습니다

다섯 장짜리 덱에서 **2번 장**만 건너뛰기로 표시하고, 브라우저가 서버에 요청한
슬라이드 번호를 그대로 받아 적었습니다.

```
프로젝터가 그린 덱 슬라이드 : [1, 2, 3, 4]
발표자 창이 그린 덱 슬라이드: [1, 2, 3, 4]
보여야 하는 것             : [1, 3, 4, 5]
```

세 가지가 한꺼번에 틀렸습니다.

1. **건너뛰라고 표시한 2번 장을 그대로 띄웠습니다.**
2. 그 뒤의 모든 장에 **한 칸씩 밀린 번호**가 붙었습니다.
3. **5번 장은 발표 내내 한 번도 나오지 않았습니다.** 덱의 마지막 장이 닿을 수 없는
   곳에 있었습니다.

## 왜 그랬나

발표는 건너뛴 장을 뺀 목록을 들고 시작합니다(`slidesToPresent`). 그런데 슬라이드를
그리는 모든 곳이 그 목록의 **자기 자리 번호에 1을 더해** 서버에 요청했습니다.

```js
api.slidePreview(presentationId, position + 1, width)   // ← 쇼의 자리 번호
```

쇼는 덱이 아닙니다. 2번을 뺀 쇼의 두 번째 자리는 **덱의 3번 장**인데, `position + 1`은
2를 보냅니다. 쇼가 네 장이므로 요청은 4에서 멈추고, 덱의 5번 장에는 영영 닿지
않습니다.

발표자 창은 여기에 더해 **덱 전체**를 받고 있었습니다. 그 파일의 주석은 이렇게
적혀 있었습니다.

> 이 창은 스스로 위치를 갖지 않으므로 — 발표 창이 위치를 쥐고 이 창은 따라가므로 —
> 두 창이 어느 슬라이드가 올라와 있는지를 두고 어긋날 수 없습니다.

같은 계산 실수를 양쪽이 똑같이 하고 있었던 덕분에 두 창은 어긋나지 않았습니다.
대신 **둘 다 같이 틀렸습니다.**

## 무엇을 고쳤나

쇼가 **자기 자리를 세는 대신 덱의 번호를 들고 다니게** 했습니다. 그리는 훅 두 개는
이제 장수가 아니라 덱 번호 목록을 받습니다.

```js
useSlideDrawings(presentationId, positions, version, index)
//                               ^^^^^^^^^ [1, 3, 4, 5]
```

`showPositions(slides)` 하나가 그 목록을 만들고, 발표 창·발표자 창·개요 격자·한 줄씩
내놓는 슬라이드의 마크업 요청이 모두 같은 목록을 씁니다. 발표자 창에는 이제
**덱이 아니라 쇼**를 넘깁니다.

슬라이드 안의 `#slide-N` 링크도 함께 고쳤습니다. N은 **덱의 번호**이므로 쇼에서
그 자리를 찾아 가고, 가리키는 장이 건너뛰기라면 그 다음으로 나오는 장으로
갑니다 — 그 장에는 설 자리가 없기 때문입니다.

고친 뒤 같은 측정:

```
프로젝터가 그린 덱 슬라이드 : [1, 3, 4, 5]
발표자 창이 그린 덱 슬라이드: [1, 3, 4, 5]
발표자 창 카운터           : 4 / 4
```
