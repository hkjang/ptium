# Ptium v1.48.1

**템플릿 네 개를 동시에 올리면 서버가 죽었습니다.**

## 1.48.0에서 파드 제한을 올리고, 그 근거를 다시 확인하다가

설치 문서는 파드 메모리가 "템플릿 분석"을 위한 것이라고 적고 있습니다. 그 말이
맞는지 재 봤습니다. 설정이 허용하는 최대 크기는 **64 MB**입니다.

```
30 MB 템플릿 1개   →  201 · 1.2초 · 최대 176 MiB
60 MB 템플릿 1개   →  201 · 2.3초 · 최대 441 MiB
60 MB 템플릿 2개   →  201·201 · 2.7초 · 최대 715 MiB
60 MB 템플릿 4개   →  ✗ OOMKilled — 프로세스가 죽음
```

네 명이 동시에 올리면 파드가 죽습니다. 그리고 그때 **그 순간 처리 중이던 무관한
요청들도 함께 죽습니다** — 발표를 내보내던 사람, 덱을 저장하던 사람까지.

설정은 64 MB를 받아들이고, 동시에 몇 개까지인지는 아무도 정하지 않고 있었습니다.
**제품이 지킬 수 없는 것을 받아들이고 있었던 것입니다.**

## 이제 한 번에 하나씩 읽습니다

업로드는 **본문을 읽기 전에** 자리를 잡습니다 — 바이트가 메모리에 들어오는 순간부터
비용이 발생하므로, 읽고 나서 재는 것은 늦습니다.

```
고치기 전:  60 MB × 4  →  프로세스 사망
고친 뒤:    60 MB × 4  →  201 네 개 · 6.2초 · 최대 798 MiB
고친 뒤:    60 MB × 8  →  201 여덟 개 · 16.4초 · 최대 470 MiB
```

30초를 기다려도 자리가 나지 않으면 매달아 두지 않고 `503 templates_busy` 로
답합니다 — 가장 큰 템플릿도 2초면 읽으므로 열두 개쯤의 대기열까지는 여유가 있습니다.

처음에는 동시 2개까지 허용했는데, 갓 시작한 프로세스에서는 통과하고 **일하던
프로세스에서는 죽었습니다**(먼저 읽은 것이 아직 운영체제로 돌아가지 않아서).
그래서 하나로 정했습니다. 재 보지 않았으면 못 봤을 차이입니다.

## 곁들여

설정 서비스가 없을 때 업로드 경로가 nil 역참조로 죽는 자리 두 곳도 막았습니다.
실제 배포에서는 항상 있지만, 없을 때 죽을 이유는 없습니다.
