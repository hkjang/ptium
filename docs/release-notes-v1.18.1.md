# Ptium v1.18.1

어제 낸 PDF 리더를, **PDF를 보내는 사람이 착한 사람이 아닐 때**를 기준으로 다시 봤습니다.
가져오기는 누구든 파일을 올릴 수 있는 자리이고, 리더는 그 파일을 가장 먼저 만지는 코드입니다.

## 100KB 파일 하나가 서버를 세울 수 있었습니다

직접 만들어 재 봤습니다.

- 공백 100MiB를 zlib으로 압축하면 **약 100KB**입니다.
- 한 쪽이 그 스트림을 **60번 참조**하도록 적습니다.
- 파일 전체는 **100KB**. 압축 해제하면 **수 GB**입니다.

이 파일을 넣었더니 **10분이 지나도 끝나지 않았습니다.** 측정한 할당량은 **5,409MiB**였습니다.
누구든 100KB를 올려서 서버를 멈출 수 있었다는 뜻입니다.

### 세 가지 한계를 정했습니다

숫자는 짐작이 아니라 **실제 파일 52개를 재서** 골랐습니다.

| | 실측 최대 | 정한 한계 |
| --- | --- | --- |
| 한 쪽의 내용 | 1.9 MiB (혼인관계증명서) | **8 MiB** |
| 한 문서가 푸는 총량 | 6.0 MiB (127쪽 거래내역서) | **64 MiB** |
| 스트림 하나 | — | **16 MiB** |

읽어야 할 파일보다 훨씬 위, 노리고 만든 파일보다 훨씬 아래입니다. 같은 공격 파일이
**10분 이상 · 5,409MiB → 0.05초 · 70MiB** 가 되었습니다.

## 같은 것을 두 번 풀지 않습니다

긴 문서는 **모든 쪽이 같은 문자표를 씁니다**. 127쪽짜리는 12,249개짜리 표를 127번 풀고
127번 파싱하고 있었습니다 — 긴 파일이 느렸던 이유의 대부분입니다.

한 번 푼 스트림과 한 번 읽은 문자표를 기억합니다. 실측 52개를 읽는 시간이
**5.83초 → 3.97초**, 결과는 **글자 하나까지 동일**합니다.

## 망가진 파일

잘린 파일, 바이트가 뒤집힌 파일, 중간이 잘려 나간 파일 **636개**를 넣었습니다.
전부 오류나 빈 쪽으로 답했고, **패닉도 멈춤도 없었습니다.**

## 이어지는 장의 제목

쪽마다 제목이 없는 문서가 이어지면 제목이 `(계속) (계속) (계속)` 으로 자랐습니다.
한 번만 붙습니다. (`.docx` 쪽은 v1.18.0에서 고쳤고, PDF 경로가 남아 있었습니다.)

## 검사

새로 3개 — **작은 파일이 큰 것을 요구할 수 없다**(시간과 할당량을 함께 재고, 어느 한 쪽만
되돌려도 실패), **같은 스트림은 한 번만 푼다**, **망가진 파일도 답을 준다**. 되돌려 확인했습니다:
쪽 한계를 빼면 5,409MiB, 캐시를 빼면 두 번째 읽기에서 다시 풉니다.
