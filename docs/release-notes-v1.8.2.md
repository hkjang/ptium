# Ptium v1.8.2

v1.7.0 에서 "규칙을 지키는 문이 두 개인데 경비원이 하나뿐" 인 문제를 고쳤습니다. 나머지 경로도
같은지 대조했습니다. **모델을 호출하는 세 경로 — 설계 · 작성 · 슬라이드 다시 쓰기 — 는 모두
같은 문을 지납니다.** 우회로는 없었습니다.

그런데 대조하다 **다른 것** 을 봤습니다.

## 서버에는 생성기가 하나뿐입니다

덱을 쓰는 작업자와, 화면에서 슬라이드 하나를 다시 쓰는 사람이 **같은 생성기를 동시에** 씁니다.
그런데 요청마다 읽는 설정 — 제한 시간, 출력 토큰 한도, 생각 스위치 — 을 **그 공용 객체에 써
넣고** 있었습니다.

경합 검출기(`-race`)를 붙이자 바로 나왔습니다.

```
WARNING: DATA RACE
  Write ... applyProviderSettings() ← ReviseSlide()
  Previous write ... applyProviderSettings() ← Generate()
```

경고보다 결과가 나쁩니다. **50장짜리 덱** 이 출력 한도를 20,500 토큰으로 늘려 놓으면, 잠시 뒤
시작한 **슬라이드 하나 다시 쓰기가 그것을 8,000 으로 되돌립니다.** 진행 중이던 그 덱은 답이
중간에서 잘리고 — v1.6.4 부터 잘린 답은 실패이므로 — **오프라인 작성기로 넘어갑니다.**
같은 서버를 두 사람이 쓰면 일어나는 일입니다.

## 요청마다 자기 사본을 씁니다

이제 한 번의 실행은 생성기의 **사본** 위에서 돕니다. 공용 객체에는 아무도 쓰지 않습니다.
HTTP 클라이언트도 사본을 씁니다 — 제한 시간이 그 객체의 필드라서, 진행 중인 다른 요청 밑에서
바꾸면 같은 버그입니다. 연결을 담고 있는 transport 는 그대로 공유합니다.

**딱 하나만 공유합니다**: "이 제공자는 생각 스위치를 거부한다"는 사실. 그건 덱이 아니라 제공자에
대한 것이라 다음 실행이 다시 배울 필요가 없고, 원자적 플래그로 안전하게 나눕니다.

## 앞으로도 잡히게

- 회귀 테스트를 넣었습니다. 고친 것을 되돌리면 **경합이 다시 검출됩니다** (확인했습니다).
  `-race` 없이 돌려도, 실행이 끝난 뒤 공용 생성기가 **들어갈 때와 똑같은지** 검사합니다.
- **`make test` 와 CI 가 이제 `go test -race` 로 돕니다.** 전체 테스트를 경합 검출기로 돌려
  다른 경합이 없는 것도 확인했습니다.

## 설치

```bash
gzip -dc ptium-1.8.2.tar.gz | docker load
```
