# Ptium v1.35.0

관리자 고도화 세 번째 — **사용 현황**입니다.

## 개요는 "지금"만 말했습니다

덱이 몇 개인지, 무엇이 대기 중인지는 있었지만 **한 주가 어땠는지**는 어디에도
없었습니다 — 몇 개를 만들었고, 몇 개가 실패했고, 얼마나 걸렸고, 누가 요청했는지.
자체 호스팅 모델에서는 **그 시간이 곧 운영 비용**입니다.

## 관리자 · 사용 현황

```
3,957 (14일 동안 만든 덱)    52 실패 · 전체의 1.3%    12분 58초 가장 오래 걸린 한 덱

날짜별  ▁▃▂▅▁▇   막대는 만든 덱, 붉은 부분은 실패
누가 만들었나 · 어떤 디자인으로 · 실패한 이유
```

- **7 · 14 · 30 · 90일**로 기간을 바꿉니다.
- 하루마다 **만든 덱 · 실패 · 중앙 소요 · 가장 오래 걸린 덱**.
- **누가 · 어떤 디자인 · 왜 실패했는지** 상위 목록. 실패 이유는 작성자가 받은 문장
  그대로 묶습니다 — 같은 이유 두 건은 고칠 것이 하나입니다.

## 숫자를 정직하게 말하는 데 든 두 번의 수정

**하나 — "0초"**. 내장 생성기는 백분의 일 초에 답합니다. 초 단위로 반올림하니 모든 날이
`중앙 0초`였습니다. 읽을 수 있는 숫자가 아니라서 **소수 둘째 자리까지**, 그리고
**그날 가장 오래 걸린 덱**을 함께 답합니다 — 모델이 얼마나 걸렸는지는 그 숫자에 있습니다.

**둘 — 스스로 모순**. 반올림 자리가 달라서 어떤 날은 `중앙 0.01초`인데
`가장 오래 0초`였습니다. **가장 오래가 중앙보다 빠르다**는 말입니다. REST 훑기가 잡아
릴리스 전에 고쳤습니다(둘 다 같은 자리로 반올림).

또한 **시간을 기록한 덱이 몇 건인지** 함께 말합니다 — 기록이 없는 옛 덱에서 뽑은
중앙값은 아무도 읽어서는 안 되는 숫자입니다.

## API

```
GET /api/v1/admin/usage?days=14      (1~180, 벗어나면 422)
```

## 검사

- REST 훑기: 요청한 일수만큼 행이 오는지, 날짜 합계와 총계가 맞는지, **실패가 생성보다
  많지 않은지**, **가장 오래가 중앙보다 느린지**, 시간 기록 수가 생성 수를 넘지 않는지,
  이름 없는 행이 없는지, 범위를 벗어난 days가 422인지.
- 화면: 소요 시간 표기(밀리초·초·분), 막대 높이(가장 바쁜 날 기준, 하루 한 건도 보이게),
  실패 비율을 단위 테스트로 고정했습니다.
- 화면 훑기가 이 화면을 열고 막대가 그려지는지 봅니다. (첫 시도에서 날짜 글씨가
  10.5px로 이 제품의 최소 글씨 규칙에 걸렸고, 훑기가 잡아 고쳤습니다.)

전체 Go 테스트 · 웹 165개 · REST 609개 · deep · 화면 훑기 0 failures.
