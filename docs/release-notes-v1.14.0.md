# Ptium v1.14.0

## 키의 권한을 나중에 바꿀 수 있습니다

API 키는 한 번 만들어 서버 설정에 적어 넣고 잊습니다. 그런데 권한 하나를 더 주려면
**새 키를 발급해서 그 서버를 다시 만져야** 했습니다. 그래서 사람들은 처음부터 모든 권한을
줍니다 — 권한 범위라는 개념이 무의미해집니다.

이제 키 목록에서 **권한 수정**을 누르면 그 키가 무엇을 할 수 있는지 바꿉니다. **키 값은
그대로**이므로 쓰는 쪽은 아무것도 고치지 않아도 됩니다.

- `PATCH /api/v1/api-keys/{id}` — `{"scopes": ["presentations:read", "templates:read"]}`
- 폐기된 키는 바꿀 수 없습니다(끝난 키입니다)
- 감사 기록에 `api_key.scopes` 로 남습니다

## 권한 목록이 서버의 것이 됩니다

화면이 **자기 목록을 들고 있었고, 서버와 어긋나 있었습니다.** 빠져 있던 것 중 하나가
`templates:read` 입니다 — 서버의 **일곱 개 경로가 요구**하고 **기본 키가 항상 갖는**
권한인데, 화면에서는 줄 방법이 없었습니다. `templates:write` 와 관리자 권한 셋도
마찬가지였습니다.

이제 화면은 `GET /api/v1/api-keys/scopes` 가 주는 것을 그립니다. 서버가 검사에 쓰는 목록과
**같은 목록**입니다.

- 6개 → **11개**: 프레젠테이션 조회/편집, 템플릿 조회/업로드, 프로필 읽기/편집, API 키 관리,
  MCP 연결, 그리고 관리자에게만 보이는 설정·사용자·오류 센터
- 각 줄에 API 이름(`templates:read`)을 함께 적습니다 — 403 을 받았을 때 무엇을 켜야 하는지
  바로 보이도록
- 화면이 모르는 새 권한이 서버에 생기면 **서버가 부르는 이름 그대로** 나타납니다

고정 검사 둘이 이 어긋남을 다시 막습니다: 서버가 받아들이는 권한은 모두 목록에 있어야 하고,
**라우팅 표가 요구하는 권한은 모두 키로 줄 수 있어야** 합니다.

## 폐기된 키는 목록에서 감춥니다

`DELETE` 는 키를 지우지 않고 폐기합니다(감사 기록이 그 키를 가리켜야 하니까요). 그래서
목록이 끝난 키로 채워졌습니다 — 개발 계정에는 89개가 쌓여 있었습니다.

이제 폐기된 키는 감추고, `폐기된 키 N개는 목록에서 감춰져 있습니다 · 보기` 로 언제든 볼 수
있습니다. **회전 유예 중인 키는 아직 동작하므로 계속 보입니다.**

## 스윕이 하던 척만 하고 있었습니다

이 작업 중에 발견했습니다. api 스윕의 API 키 검사 전체가 `key.get("token")` 을 보고 있었고,
서버는 `secret` 으로 답합니다. 그래서 **읽기 전용 키가 쓰기를 못하는지 확인하는 검사가 한
번도 실행된 적이 없고**, 키도 지워지지 않아 89개가 쌓였습니다. 이제 비밀값을 못 찾으면
스윕이 실패하고, 검사가 실제로 돕니다 (431 checks).
