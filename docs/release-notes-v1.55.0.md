# Ptium v1.55.0

**썸네일 한 장이 전체 화면 한 장과 똑같은 값을 치르고 있었습니다.**

## 주석이 한 말과 코드가 한 일

`internal/pptx/media.go`의 주석은 이렇게 적혀 있었습니다.

> 원본 이미지를 그대로 넣기에는 너무 무거우므로 — 전면 사진은 보통 1메가바이트다 —
> 각 이미지를 디코딩해 **미리보기가 실제로 그리는 크기로 축소한 뒤** 다시 인코딩한다.

축소는 했습니다. 다만 크기가 **고정 상수 1400px**이었습니다. 요청한 너비와는
아무 상관이 없었습니다.

## 쟀습니다

2400×1600, 2.4MB 사진을 한 장에 넣고, 같은 슬라이드를 네 가지 너비로 요청했습니다.

```
                        고치기 전      고친 뒤
편집기 슬라이드 레일 (260px)   968,557  →    59,109 bytes
발표 개요 격자      (320px)   968,559  →    59,111 bytes
워크스페이스 미리보기 (960px)   968,565  →   522,385 bytes
발표 화면          (1600px)  968,577  →   968,577 bytes
```

**260픽셀짜리 썸네일이 968KB였습니다.** 전체 화면과 같은 값입니다. 편집기를 열면
슬라이드 레일이 장마다 그만큼을 끌어옵니다 — 사진이 든 50장 덱이면 대략 48MB입니다.

전체 화면(1600px)은 그대로입니다. 원래도 천장에 닿아 있었으니 옳습니다.

## 어떻게 고쳤나

그림을 그릴 자리를 아는 곳이 이미 두 군데 있었습니다. 미리보기의 좌표는 EMU가
아니라 **CSS 픽셀**로 나가므로, 그 상자의 크기가 곧 그려질 픽셀 수입니다. 그래서
따로 배관을 놓을 필요가 없었습니다.

```go
uri := mediaDataURI(name, data,
    pictureBox{Width: width, Height: height, Cover: cover}, previewImagePixels)
```

`pictureBox.budgetFor`는 그림의 실제 치수와 상자를 함께 보고, 그려질 크기에
고밀도 화면 몫으로 2배를 곱해 가장 긴 변의 예산을 냅니다. **1400px는 목표가 아니라
천장으로 남았습니다** — 이 계산은 전보다 더 많이 요구할 수 없습니다.

잘라내기(`cover`)를 따로 봅니다. 잘리는 그림은 상자를 덮을 때까지 확대되므로,
보이는 부분이 그림의 더 적은 픽셀에서 나옵니다. 상자만 보고 예산을 잡으면 바로
그 경우가 흐려집니다.

## 그리고 개요 격자

값이 싸지고 나서야 고칠 수 있던 것이 하나 더 있었습니다. 발표 중 **G**를 눌러 여는
슬라이드 격자입니다. 뛰어갈 장을 찾으려고 여는 화면인데, 이 격자는 **현재 장의
이웃**만 요청하고 있었습니다.

```
덱 8장 · 개요 격자: 칸 8 · 그림 3 · 빈 칸 5      ← 고치기 전
덱 8장 · 개요 격자: 칸 8 · 그림 8 · 빈 칸 0      ← 고친 뒤
```

여덟 칸 중 다섯 칸이 번호만 적힌 회색 상자였습니다. 이제 전부 그리되, **지금 장에서
가까운 것부터** 받아 옵니다 — 발표자가 보고 있는 곳이 거기이기 때문입니다.
