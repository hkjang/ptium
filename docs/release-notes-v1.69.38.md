# Ptium 1.69.38

한 네트워크 뒤에 앱이 스무 개 있습니다. 하나의 Keycloak 을 두고도 앱마다 같은 로그인
화면을 보여 주고 있었고, 저마다 방문자를 세면서 같은 질문에 같은 답을 내는 앱이
없었습니다. 이번 판은 그 둘을 다룹니다. **둘 다 꺼진 채로 나갑니다** — 켜기 전까지
새로 설치한 곳은 이전과 바이트 하나 다르지 않게 움직입니다.

## 1. 제공자가 이미 아는 사람은 로그인 화면 없이 들어옵니다

**관리 → 서비스 설정 → OIDC · SSO** 에 **자동 로그인**(`auth.oidc.auto_login`, 기본
**사용 안 함**)이 생겼습니다. 켜면, 세션이 없는 브라우저가 페이지를 열었을 때 로그인
화면을 보이기 전에 제공자에게 `prompt=none` 으로 **한 번** 묻습니다. 제공자에 세션이
있으면 코드가 돌아와 평소 로그인 흐름으로 이어지고, 깊은 링크로 들어온 사람은 그
자리로 돌아갑니다. 없으면 `error=login_required` 가 돌아옵니다 — 이것은 오류가 아니라
"아무도 로그인하지 않았다"는 대답이고, 그때 로그인 화면이 뜹니다.

### 일의 전부는 그 두 번째 대답을 한 번만 받는 것입니다

`prompt=none` 은 화면을 그리지 않습니다. 거절을 받고 다시 물으면 브라우저는 사람이
깜빡임을 보고 있는 동안 제공자와 이 앱 사이를 오갑니다. 그래서 서로 다른 것을
견디는 장치 셋을 둡니다.

- **탭마다 한 번**의 표시를 `sessionStorage` 에 남깁니다. 새 탭은 다시 묻고, 거절 뒤의
  새로고침은 묻지 않습니다.
- **로그아웃**이 남기는 표시는 세션이 다시 생길 때 지워집니다. 로그아웃이 제공자 세션에
  의해 되돌려지는 것처럼 보이지 않습니다.
- 거절 자체를 주소에 둡니다 — `/login?sso=none`. 저장소가 비워져도 남습니다.

읽을 수 없는 저장소 — 사생활 보호 창 — 는 **이미 물은 것**으로 칩니다. 그것을 "아직"
으로 읽는 것이 곧 그 되풀이이기 때문입니다. 콜백, 로그인 화면, 공유된 덱, `/api` ·
`/mcp` · 상태 점검 아래에서는 애초에 시작하지 않습니다.

켜는 것은 설정뿐입니다. 서버는 `/api/v1/auth/config` 를 물을 때 읽고(시동 때가 아니라,
그래서 재시작이 필요 없습니다), 브라우저는 그 응답이 `autoLogin` 이라고 할 때만
`prompt=none` 을 붙입니다. 호출자나 주소로는 켤 수 없습니다. 숨은 iframe 이 아니라
최상위 이동을 쓰므로 서드파티 쿠키가 막힌 곳에서도, 제공자가 프레임을 허용하든 말든
동작합니다.

## 2. 관리자가 방문 추적 스니펫을 페이지에 붙일 수 있습니다

**관리 → 서비스 설정** 에 **방문 추적** 영역이 생겼습니다 — 어떤 추적기인지, 무엇이
필요한지, 스니펫이 어디에 붙는지. `analytics.enabled` 는 기본 **꺼짐**이라 아무
페이지에도 아무것도 없고, 페이지 정책은 이전과 바이트 그대로입니다.

### 어려운 쪽은 `<script>` 가 아니라 정책입니다

워크스페이스는 자기 출처의 스크립트만 돌립니다. 붙여 넣은 스니펫은 붙인 사람에게 한
마디 없이 거절됩니다. 정책을 `'unsafe-inline'` 으로 풀지는 않습니다 — 한 번 풀린
정책은 추적을 끈 뒤에도 풀린 채로 남습니다. 대신:

- 페이지마다 **새 nonce** 를 만들어 스니펫의 모든 `<script>` 에 붙이고 `script-src` 에
  넣습니다.
- 추적기가 불러오고 보고하는 **출처를 스니펫과 제공자에서 읽어** 정책에 더합니다.
  화면의 **정책에 더해질 출처**가 저장 전에 그 목록을 보여 줍니다.
- 추적이 켜져 있는 동안 `report-uri` 로 브라우저에게 **그래도 막은 것**을 말하게
  합니다. 신고는 메모리에 출처별 한 줄씩 모이고, 영역의 **차단된 출처** 표에 **허용**
  단추와 함께 나타납니다 — 직접 적는 것과 같은 검증과 같은 이력을 거칩니다.
- 자산, `/api`, `/mcp`, 상태 점검에는 스니펫이 없고, 정책은 오히려 더 좁아졌습니다:
  `default-src 'none'`.

### Momento 가 첫 자리입니다

사내 자체 호스팅 수집기라 데이터가 네트워크를 떠나지 않는 유일한 선택지입니다. 기본으로
**이 출처를 거쳐** 닿습니다 — 브라우저는 `/momento/tracker.js` 를 받고 `/momento` 로
보고하며, 서버가 세션 쿠키와 bearer 토큰을 벗긴 채 수집기로 넘깁니다. 그래서 수집기는
정책에 등장할 필요가 아예 없습니다. GA4 · GTM · Matomo 는 측정 ID 나 주소만 넣으면
되고, 직접 붙여 넣기는 8KB 까지입니다.

### 대소문자 접기는 ASCII 만

스니펫에서 `<script` 를 찾을 때 대소문자를 접습니다. `strings.ToLower` 는 U+212A
KELVIN SIGN 과 U+0130 의 **바이트 길이를 바꾸므로**, 접은 사본에서 잡은 위치가 원본에서는
다른 자리에 떨어져 nonce 가 태그 이름 안에 써집니다. 참고한 구현이 정확히 그 결함을
갖고 있었습니다. 여기서는 ASCII 만 접습니다.

## 지키는 장치

`internal/analytics` 는 기본이 꺼짐인지, 모든 태그에 nonce 가 붙는지, 길이가 바뀌는
글자, 스니펫에서 읽어 낸 출처, 기록기가 출처 백 개를 하나씩만 드는지 봅니다.
`internal/webui/tracking_test.go` 는 실제로 주는 페이지를 봅니다 — head 나 body 의
스니펫, 정책 속 nonce, `include_admin` 일 때만 붙는 관리 화면, 자산과 새 설치가 그대로인지.
`internal/httpapi` 는 신고 엔드포인트, 스위치가 있을 때와 없을 때와 수집기가 죽었을
때의 프록시, 설정의 범위, 그리고 서버가 내는 `autoLogin` 플래그를 봅니다.

웹 쪽 `auth/oidc.test.ts` · `auth/silentSso.test.ts` · `auth/silentSsoStorage.test.tsx`
는 설정이 있을 때와 없을 때 만들어지는 요청, 제공자의 각 대답이 어디에 내려앉는지,
그리고 **묻지 않아야 하는 모든 이유**를 봅니다. `pages/tracking.test.ts` 는 화면 자체의
검사입니다.

관리자 안내서에 두 절이 있고 — 자동 로그인의 동작과 켜기 전에 확인할 것, 방문 추적과
정책의 설명 — PDF 를 다시 만들었습니다.
