# Ptium v1.48.0

**설치 문서가 적어 둔 메모리 수치가 실제의 4분의 1이었습니다.**

## 문서에 적힌 숫자를 다시 재 봤습니다

`docs/offline-deployment.md` 는 "이 빌드에서 측정함"이라며 표를 싣고 있습니다.
이번 세션에서 제품을 많이 고쳤으니 그 숫자가 아직 맞는지 재 봤습니다.

```
문서:  40장짜리 덱 4개, 각 장에 사진, 동시에 PDF 인쇄 → 0.7초 · 169 MB
실측:  같은 작업                                    → 7.1초 · 639 MiB
```

**4배 가까이 어긋납니다.** 그리고 매니페스트는 파드를 **768Mi**로 제한하고 있었으니,
문서상 22%를 쓴다는 작업이 실제로는 **83%**를 씁니다.

## 제가 만든 회귀는 아니었습니다

이번 세션 이전 이미지(1.31.3)로 같은 측정을 했습니다.

```
1.31.3 (세션 전)   7.44초 · 645 MiB
1.47.1 (현재)      6.86초 · 619 MiB
```

오래된 성질이고, 오히려 조금 나아졌습니다. 문서의 숫자가 그냥 틀렸던 것입니다 —
아마 훨씬 작은 그림으로 쟀을 것입니다.

## 무엇이 메모리를 쓰는지 찾다가, 한 번 틀렸습니다

같은 사진이 슬라이드마다 **다시 디코딩**되는 것을 발견하고(문서 40장이면 40번),
문서 단위로 한 번만 디코딩하도록 캐시를 넣었습니다. 그리고 **재 봤더니 아무 차이가
없었습니다**(646 MiB 대 619 MiB, 오차 범위).

그래서 **되돌렸습니다.** 그럴듯하지만 효과를 보이지 못한 변경은 넣지 않습니다.

## 대신 사실을 적었습니다

- 표를 **1Gi 제한 컨테이너에서 다시 측정한 값**으로 바꿨습니다. 조건도 함께 적었습니다 —
  1376×768 사진은 그리기 위해 펼치면 4 MB이고, 첫 줄을 결정하는 것은 그림입니다.
- 두 번째 줄(작은 덱 12개 동시 내보내기)은 문서의 `5초 · 87 MB` 보다 **훨씬 빨랐습니다**:
  **0.2초 · 49 MiB**. 첫 줄 직후에 측정한 값이라 "메모리가 돌아온다"는 말도 그 자리에서
  확인됩니다.
- 세 번째 줄은 이번 세션에서 실제로 돌린 값(**44,547건/분, 실패 0**)으로 갱신했습니다.
- 파드 제한을 **768Mi → 1Gi** 로 올렸습니다. 768Mi에서도 OOM 없이 끝나지만 여유가
  17%뿐입니다. 새 제한에서 같은 작업은 **63%**를 씁니다. 왜 올렸는지 매니페스트 주석에
  숫자째 적어 두었으니, 낮추고 싶다면 근거를 보고 판단할 수 있습니다.
