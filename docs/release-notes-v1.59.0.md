# Ptium v1.59.0

**MCP 도구가 말하는 것과 하는 것을 맞춰 봤습니다. 세 군데가 달랐습니다.**

에이전트는 도구 설명을 읽고 그대로 행동합니다. 설명이 사실과 다르면 사람이
잘못 읽는 것보다 조용히, 그리고 반복해서 어긋납니다.

## 1 · "51장"이 절벽에서 떨어졌습니다

브리프에 적힌 장수를 읽는 파서의 상한이 **배포의 상한과 같은 숫자(50)**였습니다.
그래서 딱 그 지점에 절벽이 생겼습니다.

```
브리프              만들어진 장수   제품이 한 말
50장짜리로 만들어 줘      50        (문제 없음)
51장짜리로 만들어 줘      10        (아무 말 없음)   ← 절벽
5000장짜리로 만들어 줘    10        (아무 말 없음)
```

51은 "덱 길이가 아닌 숫자"가 아니라 **이 배포가 들어줄 수 없는 요청**입니다. 상한
처리는 이미 v1.58.0에서 자르고 알려 주도록 고쳤는데, 파서가 그 앞에서 숫자를
삼켜 버려 아무 말도 나오지 않았습니다.

파서의 상한을 배포 상한에서 떼어 99로 올렸습니다. 파서가 정말 가려야 하는 것은
**덱 길이가 아닌 숫자**입니다 — 모든 패턴이 숫자 옆에 장·페이지·slides 같은 말을
요구하므로, 남는 것은 `이 100페이지 보고서를 요약해 줘` 같은 원본 문서입니다. 두
자리는 사람이 말한 덱 길이이고, 세 자리는 요약 대상인 쪽이 훨씬 많습니다.

```
51장짜리   → 50장 · "51장을 요청하셨지만 이 배포는 한 덱에 50장까지…"
99장짜리   → 50장 · 같은 말
100페이지 보고서를 요약 → 10장 · (여전히 덱 길이로 읽지 않음)
5000장짜리 → 10장 · (여전히 덱 길이로 읽지 않음)
```

## 2 · 거절이 호출자가 보내지도 않은 값을 탓했습니다

MCP는 상한을 넘으면 자르지 않고 거절합니다(에이전트에게는 그쪽이 낫습니다). 그런데
메시지가 `slideCount exceeds the configured generation limit`이었습니다. **장수는
브리프에서 읽어 올 수도 있습니다.** 그 경우 호출자는 보낸 적 없는 인자를 자기
코드에서 찾게 됩니다. 게다가 두 숫자 중 어느 것도 말하지 않아, 대신 무엇을
요청해야 할지 알 수 없습니다.

```
브리프에서 온 숫자   the prompt asks for 60 slides and this deployment allows 50 to a deck:
                   ask for 50 or fewer in the prompt, or pass slideCount
직접 넘긴 숫자      slideCount is 30 and this deployment allows 5 to a deck
```

## 3 · 목록 순서와 템플릿 응답

`list_presentations`는 **"newest first"**라고 했지만 정렬은 `updated_at DESC`입니다 —
지난주에 만들고 오늘 고친 덱이 한 시간 전에 만든 덱보다 위에 옵니다. 그 순서가
자기 작업 목록으로는 옳으므로, **설명을 사실에 맞췄습니다**("most recently changed
first").

`list_templates`는 **"with their layouts"**라고 했지만 응답에는 `layoutCount`만 있고
`layouts`는 없습니다. 특정 디자인으로 덱을 만들 때 실제로 필요한 것은 `id`인데 그건
언급조차 없었습니다. 둘 다 이름으로 적었습니다.

## 재 보고 문제가 없던 것

* `q`는 제목과 브리프를 모두 찾습니다
* `create_presentation`은 정말 슬라이드 없는 draft를 돌려줍니다
* `get_presentation`이 말하는 상태 이름이 실제 상태와 같습니다

이번 반복에서 측정 도구가 두 번 틀렸습니다. 템플릿 키 목록을 8개에서 잘라 놓고
