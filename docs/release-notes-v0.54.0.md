# Ptium v0.54.0

렌더한 파일 전체를 이전 기록과 비교하는 테스트를 넣었고, **그 테스트가 첫 실행에서 결함을
찾았습니다.**

## 마지막 슬라이드는 마지막이라는 이유만으로 마무리 페이지가 아닙니다

덱의 마지막 슬라이드는 보통 요청입니다. 그래서 컴파일러는 위치만 보고 마지막 슬라이드에
마무리 레이아웃을 주었습니다. 마무리 레이아웃에는 제목과 그 아래 한 줄밖에 없습니다.

그 마지막 슬라이드가 꺾은선이면 어떻게 되는가 — 이렇게 됩니다.

```
제목: 월별 처리량
  월: 1월, 2월, 3월, 4월
  전환 전: 120, 118, 121, 119
  전환 후: 120, 132, 148, 165
```

그림이 되어야 할 추이가 제목 밑 세 줄의 텍스트로 납작해집니다. 컴파일러는 경고를 남기고
있었지만, 경고는 슬라이드를 되돌려 주지 않습니다.

이제 **표나 도표를 든 슬라이드는 위치만으로 마무리가 되지 않습니다.** 저자가 `@closing` 이라고
직접 쓰면 그대로 따릅니다 — 위치는 추측이고, 저자는 결정이기 때문입니다. 같은 규칙이 이미 첫
슬라이드에는 있었습니다(내용을 든 첫 장은 표지가 아닙니다). 이번에 반대쪽 끝을 맞췄습니다.

고친 뒤 그 슬라이드는 **진짜 차트 부품**(`ppt/charts/chart1.xml` + 열어서 고칠 수 있는
워크북)으로 나갑니다.

## golden 파일 비교 (로드맵 7차)

`server/internal/golden` — 렌더한 `.pptx` 를 통째로 텍스트 개요로 펼쳐 기록해 둔 것과 비교합니다.
부품 목록, 콘텐츠 타입, 관계, 그리고 슬라이드 · 레이아웃 · 마스터 · 테마의 **모든 요소와 속성**.

나머지 테스트는 덱이 *무엇을 말하는지*를 봅니다 — 이 글이 넘쳤다, 저 수치에 출처가 없다.
파일은 어떤 측정도 눈치채지 못하는 방식으로 틀릴 수 있습니다: 한쪽에 선언되고 다른 쪽에 없는
부품, 아무 데도 닿지 않는 관계 id, 상속이 끊긴 레이아웃. 그건 PowerPoint가 저자에게 알려 주지,
우리에게 알려 주지 않습니다.

- 실패하면 **바뀐 첫 줄과 주변 세 줄만** 보여 줍니다. 2,400줄짜리 diff는 아무 말도 하지 않습니다.
- 의도한 변경이면 `go test ./internal/golden -update` 로 다시 기록합니다.
- 같은 입력이 두 번 같은 파일을 내는지도 따로 확인합니다. 흔들리는 기준은 기준이 아닙니다.
